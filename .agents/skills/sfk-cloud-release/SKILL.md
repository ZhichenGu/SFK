# SFK 云端变更与发布

本 Skill 处理部署与数据库变更的目标、兼容性和结果验证。普通本地开发无需加载；用户只要求方案时交付可执行方案，不自动部署。

## 先确定目标与授权

从当前请求、仓库远程地址、`config.js`、`supabase/config.toml` 和 README 中按需确定目标。文件里的项目 ID、密钥或旧部署记录是配置证据，不是本次执行授权。目标矛盾时澄清；已确认的操作与目标不重复询问。

准备本地差异、SQL 或部署命令不需要额外批准。执行提交、推送、部署、云端 SQL、真实数据写入或真实 OCR 付费调用前，核对本次授权覆盖的动作。缺少授权时先完成独立准备，再只询问缺少的具体操作。

## 按变更类型处理

- **SQL**：以 `supabase.sql` 为当前建表与 RPC 定义，检查已有表和函数的兼容性、校验、返回字段、RLS 与 execute 权限。修改现有部署时优先提供针对性迁移，不假定整份初始化脚本适合原样重跑。标出锁表、重建列或数据转换影响，破坏性变更先准备恢复路径。隔离数据库检查与真实项目执行分别报告。
- **GitHub Pages**：保留静态入口、脚本顺序、相对路径、字体资源和 `siteUrl`。推送可能触发 Pages 发布，不能把推送当作无外部影响的保存。部署后按实际配置核对目标 URL 与关键资源，不能仅凭本地页面能打开宣称发布成功。
- **OCR Edge Function**：保留 `ocr-schedule` 接口，Google 凭证只放服务端 Secret。核对 CORS、请求大小、错误和超时路径；缺少 Secret 时可以完成代码与本地验证。真实识别调用需覆盖费用与数据上传的授权，不要求用户把 Secret 粘贴进聊天或前端。

## 结果与恢复

外部操作结果不确定时先查询部署、数据库对象或记录状态，避免盲目重复。授权范围不变且重试安全时可继续；目标或破坏性影响变化则重新确认。

完成时报告实际改动、目标、执行结果与对应验证。失败时保留本地成果并说明当前外部状态；未执行的 SQL、未部署的代码和模拟接口测试不算线上完成。
